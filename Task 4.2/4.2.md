### Таблица: горизонтальное масштабирование, ограничения и решения

| ИТ‑система | Реализация горизонтального масштабирования | Ограничение | Описание решения для ограничения |
| --- | --- | --- | --- |
| **BFF (Mobile)** | Развёртывание в Kubernetes с автоскейлингом по CPU/RQ (requests per second). Каждый экземпляр BFF stateless, состояние хранится в Redis (correlation ID, статусы SAGA, кэш валидности полисов). Балансировка через NGINX/API Gateway. | **Shared‑state в Redis может стать узким местом** при пиковой нагрузке: рост latency в Redis приводит к деградации всех экземпляров BFF. | Внедрить шардирование по patientId в Redis, выделить отдельный кластер Redis для критичных ключей (SAGA, идемпотентность), настроить алертинг на lag и hit rate. Использовать TTL и инвалидацию по событиям, чтобы не накапливать лишнее. |
| **1С: Полисы** | Горизонтальное масштабирование реализуется **не на уровне 1С**, а через **кэширующий слой (Redis) + адаптер с Circuit Breaker**. На стороне BFF/адаптер делается запрос в Redis; при промахе — вызов 1С. Инвалидация кэша — по событиям из CRM/1С. Таким образом, реальные запросы к 1С сокращаются в разы. | **Ограниченная ёмкость 1С**: даже при кэшировании остаются «горячие» сценарии (новые полисы, частые проверки), где 1С остаётся узким местом. | Для срочных кейсов реализовать **приоритизацию и квотирование запросов к 1С** (rate limiting на адаптере): жёсткие лимиты на RPS по типам операций (например, «проверка полиса» — не более 40 RPS суммарно). Для остальных сценариев — fallback с сообщением «проверка временно недоступна» и рекомендацией повторить позже. |

## Почему именно эти системы критичны для SLA 50000 пользователей

* **BFF** — это «лицо» бэкенда для мобильного приложения: все запросы проходят через него. Если BFF не масштабируется горизонтально, то при пике 50000 пользователей время отклика превысит 1 сек. Stateless‑архитектура и автоскейлинг позволяют линейно наращивать мощность.
* **1С** — классический Legacy‑узкий канал: не умеет масштабироваться горизонтально, а длительные ответы «вешают» потоки в BFF и нарушают SLA. Поэтому масштабирование здесь — через **снижение нагрузки** (кэш, rate limiting, Circuit Breaker), а не через увеличение мощности 1С.
