| Интеграция / поток данных | Паттерн / стиль | Обоснование и как именно используется |
| --- | --- | --- |
| Мобильное приложение → API Gateway | REST over HTTPS + JWT + rate limiting | Защита от всплесков, единая аутентификация, возможность быстро отключить проблемные эндпоинты. Rate limiting обязателен для 50 тыс. пользователей и SLA \<1 сек. |
| API Gateway → BFF | Внутренний REST + correlation ID + идемпотентные ключи | Correlation ID нужен для distributed tracing (закрывает INT‑007). Идемпотентные ключи решают дубли записей (INT‑005) и двойные списания (INT‑001). |
| BFF → Расписание / CRM | REST API + идемпотентность на уровне запроса и БД | Устраняет дублирование записей при повторных POST. На уровне БД — уникальные ограничения и транзакции. |
| BFF → 1С (через адаптер) | REST + circuit breaker + кэш Redis + TTL | 1С нестабильна на пиках: circuit breaker предотвращает каскадные отказы, Redis снижает количество вызовов, TTL гарантирует актуальность. |
| BFF → Платёжный шлюз | REST + идемпотентные платежи + статус‑опрос (webhook/polling) | Двойные списания (INT‑001, SD‑009) решаются идемпотентностью; статус фиксируется даже при таймаутах. |
| LIS → Kafka | Публикация событий + дедупликация по ключу | FTP ненадёжен (INT‑002, SD‑005): Kafka гарантирует доставку, порядок по patient_id, потребители обрабатывают события без дублей. |
| Расписание → Kafka | Публикация событий BookingCreated/Cancelled | Позволяет CRM, уведомлениям и аналитике реагировать на изменения без синхронных вызовов. |
| CRM / Уведомления → Kafka | Подписка на события (consumer groups) | CRM обновляет данные асинхронно, уведомления отправляются по событиям — это устраняет задержки и переполнение очередей (SD‑006). |
| 1С → Redis | Адаптер с кэшированием и инвалидацией по событию | Снижает нагрузку на 1С, ускоряет ответы до \<2 сек, закрывает INT‑003. |


## Комбинация паттернов:

* **Circuit breaker + Retry + Kafka**: при падении 1С circuit breaker «размыкает» вызовы, retry с экспоненциальной задержкой пытается восстановить соединение, а Kafka накапливает события, чтобы не потерять данные. Это даёт отказоустойчивость при пиках.
* **Идемпотентность + distributed tracing**: идемпотентные ключи передаются через correlation ID по всей цепочке (Gateway → BFF → Legacy), а distributed tracing позволяет быстро найти, где именно произошёл сбой (INT‑007).
* **Кэш + инвалидация по событиям**: Redis хранит валидность полиса; при изменении в 1С публикуется событие, которое инвалидирует кэш. Это обеспечивает баланс скорости и актуальности.
* **Event‑driven + REST**: синхронные REST‑запросы используются для быстрых операций (чтение кэша, валидация), а события в Kafka — для долгосрочных процессов (загрузка анализов, отправка уведомлений, синхронизация CRM).
