## Текстовое описание решения

Для доставки результатов анализов в мобильное приложение «Здоровье+» предлагаю **event‑driven архитектуру на базе Apache Kafka** с адаптерами у источника (LIS) и приёмника (CRM/BFF), дедупликацией по уникальному идентификатору анализа и гарантированной доставкой через семантику at‑least‑once + контроль дублей на уровне потребителя.

### Как это решает проблемы текущего процесса

* **Гарантированная доставка**: вместо ненадёжного FTP используется Kafka с ретеншеном и повторными попытками. Если CRM временно недоступна, события сохраняются в топике и обрабатываются позже.
* **Минимальная задержка**: асинхронная доставка по событиям (event streaming) убирает ручные действия и таймауты скриптов. Целевое время доставки — до 1–2 минут после готовности результата.
* **Отсутствие дублей**: ключ партиционирования — `analysis_id` (или `patient_id + analysis_id`), а на стороне потребителя — дедупликация по этому ключу (например, через Redis).
* **Устойчивость к пикам**: Kafka буферизует всплески нагрузки (до 50 тыс. пользователей), а потребители масштабируются горизонтально.
* **Простота эксплуатации**: исключаются ручные операции лаборантов; мониторинг строится на стандартных метриках Kafka (lag, throughput) и health‑check адаптерах.

### Детали реализации

* **Адаптер LIS → Kafka**: забирает результаты из LIS (вместо FTP), формирует событие `AnalysisResultAvailable` и публикует в топик `analysis.results`.
* **Топик Kafka**: настроен с достаточным ретеншеном (например, 7 дней), репликацией и мониторингом лага.
* **Потребитель CRM**: подписывается на топик, дедуплицирует по `analysis_id`, обновляет CRM и публикует событие `AnalysisSynced`.
* **BFF для мобильного приложения**: либо читает данные из CRM (с кэшем Redis), либо напрямую слушает события для быстрого отображения статуса «результат готов».
* **Трассировка и алертинг**: correlation ID и distributed tracing сквозным образом связывают событие от LIS до отображения в приложении; алерты на рост лага и ошибки обработки.

## Таблица сравнения архитектурных решений

| Вариант реализации | Плюсы | Минусы | Соответствие требованиям | Почему не выбран |
| --- | --- | --- | --- | --- |
| FTP + ручной запуск (текущий) | Простота первоначальной настройки | Потеря файлов, таймауты, дубли, ручное восстановление, задержки до 2 часов | Не гарантирует доставку, не выдерживает пиков, сложно эксплуатировать | Вызывает проблемы: SD‑005, INT‑002, INT‑008 |
| Прямой REST от LIS к CRM | Понятная синхронная логика | Не выдерживает пиков (1С и CRM падают), нет буферизации, каскадные отказы, сложно обеспечить идемпотентность | Нет гарантии доставки при сбоях, плохо масштабируется | При пиковой нагрузке 50k пользователей синхронные вызовы приведут к деградации |
| RabbitMQ + очереди | Асинхронность, dead‑letter queue, TTL | Ограниченная масштабируемость по сравнению с Kafka, сложнее обеспечить порядок событий по пациенту/анализу | Частично соответствует, но хуже для потоковой обработки и порядка событий | Для гарантированного порядка и хранения истории Kafka предпочтительнее |
| Kafka + event streaming (выбранный) | Гарантированная доставка (retention, replication), порядок по ключу, горизонтальное масштабирование, буферизация пиков, дедупликация по ключу | Более сложная инфраструктура, требуется обучение команды | Полностью соответствует: гарантия, низкая задержка, масштабируемость, простота эксплуатации при правильной настройке | Оптимальный баланс надёжности, производительности и управляемости для кейса |


@startuml AnalysisDeliverySequence
title Последовательность доставки результатов анализов

actor "Лаборант / LIS" as LIS
participant "Adapter LIS→Kafka" as Adapter
queue "Kafka: analysis.results" as Kafka
participant "Consumer CRM" as Consumer
database "CRM DB" as CRMDB
database "Redis (dedup & cache)" as Redis
participant "BFF (Mobile)" as BFF
participant "Мобильное приложение" as Mobile

== Генерация и доставка события ==

LIS -> Adapter: событие AnalysisResultReady (resultId, patientId, fileUrl, metadata)
Adapter -> Kafka: отправить сообщение в топик analysis.results
Kafka --> Adapter: подтверждение записи

activate Consumer
Kafka -> Consumer: доставка сообщения (at-least-once)
activate Consumer

Consumer -> Redis: проверить наличие ключа resultId
alt resultId уже есть (дубль)
    Redis --> Consumer: ключ найден
    deactivate Consumer
else resultId отсутствует (новая запись)
    Redis <-- Consumer: ключ не найден
    Consumer -> Redis: SET resultId (TTL 30 дней)
    note right: защита от дублей
    
    Consumer -> CRMDB: INSERT/UPSERT результата анализа
    CRMDB --> Consumer: подтверждение сохранения
    
    note right: параллельно можно отправить событие для инвалидации кэша в BFF
    
    deactivate Consumer
end

== Получение данных мобильным приложением ==

Mobile -> BFF: GET /analysis-results?patientId={id}
activate BFF

BFF -> Redis: GET patient:{patientId}:analysis:*
activate Redis
alt кэш есть
    Redis --> BFF: данные из кэша
    deactivate Redis
    BFF --> Mobile: ответ со списком результатов
else кэш отсутствует
    Redis --> BFF: кэш пуст
    deactivate Redis
    
    BFF -> CRMDB: SELECT результаты для patientId
    activate CRMDB
    CRMDB --> BFF: возврат данных
    deactivate CRMDB
    
    BFF -> Redis: SET кэш (TTL 15 минут)
    activate Redis
    Redis --> BFF: подтверждение записи
    deactivate Redis
    
    BFF --> Mobile: ответ со списком результатов
end
deactivate BFF

@enduml
