## Схема аутентификации пользователей мобильного приложения

**Протокол:** OAuth2 + OIDC (OpenID Connect) с потоком PKCE (Proof Key for Code Exchange).
**Способ передачи токена:** Bearer‑токен (JWT) в HTTP‑заголовке Authorization: Bearer \<token\> для всех авторизованных запросов.

### Шаги:

1. **Пользователь вводит логин/пароль в мобильном приложении.** Приложение не хранит пароль, а инициирует OAuth‑поток с PKCE.
2. **Приложение перенаправляет пользователя на Identity Provider (IdP)** (например, Keycloak) через системный браузер ОС. Это предотвращает перехват учётных данных вредоносными приложениями.
3. **Пользователь аутентифицируется на стороне IdP.** IdP проверяет логин/пароль и возвращает код авторизации в приложение через redirect URI (deep link).
4. **Мобильное приложение обменивает код на токены**, используя PKCE‑верификатор. В ответ получает:
   * access_token (JWT, короткий TTL, например, 15 минут) — для доступа к API;
   * refresh_token (не JWT, хранится в защищённой области ОС: TTL 7–14 дней) — для получения новых access‑токенов.
5. **Для каждого запроса к API** мобильное приложение добавляет заголовок Authorization: Bearer \<access_token\>. BFF/API Gateway проверяет подпись JWT, срок действия.
6. **При истечении access_token** приложение автоматически использует refresh_token для получения новой пары токенов. При ошибке refresh (например, отзыв сессии) — пользователь выводится на экран входа.

Rel(patient, mobile, "вводит логин/пароль")
Rel_D(mobile, idp, "OAuth2+OIDC, PKCE, через системный браузер")
Rel(idp, patient, "аутентификация + MFA")
Rel_D(idp, mobile, "authorization code → обмен на access/refresh token")
Rel_D(mobile, gateway, "Запрос API с Authorization: Bearer <access_token>")
Rel_D(gateway, bff, "валидация JWT (signature, exp, aud, iss)")
Rel_D(bff, idp, "опционально: introspection endpoint для проверки отзыва токена")

## Политика Rate Limiting

| Тип запроса | Лимит | Действие при превышении |
| --- | --- | --- |
| Публичный: «Поиск врачей» (GET /doctors?search=...) | 100 запросов в минуту на IP‑адрес | Возвращать 429 Too Many Requests с заголовком Retry-After: 60. В теле ответа — сообщение «Превышен лимит запросов. Повторите попытку через 60 секунд». Логировать IP и количество запросов для выявления сканирования. |
| Авторизованный: «Создание записи к врачу» (POST /appointments) | 5 запросов в минуту на patientId (или на pair patientId + deviceId) | Возвращать 429 с Retry-After: 120. Отклонять дальнейшие попытки создания записи без повторной проверки бизнес‑логики (защита от ботов и спама). Включить алерт в мониторинг при \>3 срабатываниях за 5 минут на одного пациента. |

Реализуется на уровне API Gateway (NGINX, Kong, Yandex API Gateway и т.п.) с хранением счётчиков в Redis (скользящее окно), так как для публичного поиска важна защита от DDoS по IP; для создания записи — защита от автоматических бронирований и дублей (INT‑005), поэтому лимит привязывается к идентификатору пользователя.


## Меры защиты каналов передачи данных и периметра (с учётом mTLS, DDoS, эксплуатации)

1. **Защита от DDoS (4 рубежа):**
   * **CDN (Cloudflare/AWS CloudFront)** — первый рубеж: фильтрация трафика, блокировка по IP/гео, смягчение объёмных атак до попадания в инфраструктуру.
   * **WAF** — второй рубеж: блокировка известных атак, правила по частоте запросов на уровне приложения.
   * **API Gateway** — третий рубеж: rate limiting, проверка JWT/API‑ключей, валидация схемы запроса, отсев неаутентифицированных вызовов.
   * **Сервисы** — четвёртый рубеж: Circuit Breaker, таймауты, идемпотентность, контроль бизнес‑правил.
2. **mTLS для межсервисных взаимодействий:**
   * Применяется между API Gateway и всеми внутренними сервисами, а также между критичными сервисами (BFF ↔ 1С‑адаптер, BFF ↔ платёжный адаптер).
   * Сертификаты выдаются и ротируются автоматически через cert-manager в Kubernetes или централизованно через Vault.
   * Срок действия сертификатов — короткоживущие (2–4 часа), чтобы скомпрометированный сертификат быстро терял силу.
   * Отзыв доступа: централизованный механизм отзыва и политика немедленного перевыпуска при инциденте.
   * Мониторинг: алерты на истечение срока действия сертификатов (за 24–48 часов до окончания), автотесты на успешное установление mTLS‑сессии.
3. **Защита передачи данных между мобильным приложением и API:**
   * Обязательный TLS, запрет устаревших шифров и downgrade.
   * Certificate Pinning в мобильном приложении для критичных эндпоинтов (авторизация, платежи, получение ПДн).
   * HSTS на шлюзе.
4. **Защита от SQL‑инъекций и других L7‑угроз:**
   * Валидация и нормализация входных данных на API Gateway/BFF: whitelist‑валидация, ограничение длины, запрет спецсимволов.
   * Параметризованные запросы и ORM на уровне сервисов БД; полный отказ от склеивания SQL‑строк.
   * WAF‑правила для блокировки шаблонов SQLi/XSS до попадания в BFF.
5. **Защита от подмены сессии и злоупотребления токенами:**
   * JWT с проверкой подписи, срока действия, аудитории (aud) и издателя (iss).
   * Привязка refresh‑токенов к защищённым хранилищам ОС (Keychain/Android Keystore).
   * Механизм отзыва токенов (blacklist/revocation list) при подозрительной активности.
6. **Эксплуатационная безопасность и дисциплина:**
   * Централизованное управление секретами и сертификатами (Vault/cert‑manager).
   * Автоматические пайплайны ротации сертификатов до истечения срока.
   * Тесты на rate limiting: циклические запросы для проверки срабатывания 429 и корректности заголовков.
   * Тесты DDoS‑защиты: имитация всплеска трафика с одного IP и проверка блокировки на уровне CDN/WAF.
7. **Логирование и мониторинг:**
   * Логирование всех запросов с correlation ID, без хранения полных ПДн (только маскированные данные).
   * Отдельные алерты: всплески 429, рост ошибок mTLS, аномалии в поведении пользователей (много записей подряд, частые поиски).
   * Трассировка (OpenTelemetry) для быстрого поиска цепочки вызовов при инцидентах.
